## 结论

**已验证：局部配置有独立回读支持，全天完整业务目标尚不能验收。** 用户目标包含配置对齐和真实单据验证，因此模型状态、执行状态与实际单据行为分别判断。

- Oracle row 1597：字段属性写入曾超时，随后在新页面重新打开模型读取，确认目标属性匹配。可验收该属性的最终配置状态；返回同时标记未发生变更，不能据此计为一次确定的新增修改，也不能延伸为真实单据联查功能已验收。
- Oracle row 2577 的关联独立回读：规则查询返回成功，目标规则存在、启用且表达式匹配。可确认配置状态；尚不能证明实际保存、提交时的拦截行为。

**存在偏差：执行成功与业务成功出现分离，另有调用参数和收尾参数错误。**

- Oracle row 2045：虽然执行状态为成功，业务返回却是节点未找到、页面未呈现。该次打开目标页面的步骤未达成，不能归入业务成功。
- Oracle row 28：执行用途参数不符合工具枚举，调用被拒绝。后续修正后同一步骤执行成功，但结果仅说明字段已暂存，不能替代持久化及业务回读。
- Oracle row 144：`run_get` 揭示前序脚本因目标 DOM 容器不存在而失败；后续调整定位后读取成功。这是前序脚本失败，不能解释为状态查询工具失效。
- Oracle row 2577：收尾因记忆决策参数不完整被拒绝；后续修改决策又触发一次参数错误，第三次调用才获受理并进入收尾状态。收尾失败不推翻已有配置回读，获受理也不等同最终清理完成（关联原证据行 25079、25093、25096）。
- Windows row 3499、3554：分别确认请求冲突和收尾参数错误；对应录制会话最终记录为失败，并带 1 个验证引用。不能因同一会话中存在成功操作而改判整体成功。

**证据不足：** Oracle row 15 证明完成了一次基线读取，未证明修改完成；Windows 的成功返回证明调用层面成功，但不足以验收其具体业务目标。现有证据不支持宣称当天所有配置及真实单据验证全部完成。

## 建议

1. **补齐包装调用归因。** 将内部调用序号、条件分支是否执行、异步完成结果关联到具体记录。验收时能从一条包装记录定位实际执行与最终返回；未执行分支应明确标识，不能继承外层成功。
2. **分别记录执行结果和业务结果。** 针对 row 2045，执行成功但节点未找到时，应显示该业务步骤未达成。验收时可同时看到执行状态、页面呈现结果与对应回读依据。
3. **保留超时后的独立读取。** 延续 row 1597 的处理方式，先重新读取最终状态，再决定是否重试。验收时能区分写入是否确定发生、目标状态是否匹配，以及真实单据行为是否完成验证。
4. **修正已出现的调用参数问题。** row 28 按工具用途枚举调用；row 2577 按实际记忆使用情况填写收尾参数。验收以请求不再被同类参数错误拒绝、且后续回读到最终状态为准。
5. **补齐业务与会话闭环。** 为缺少结果的 Windows 任务补充最终状态和验证引用；配置回读与真实单据验证分别保留证据。验收时每项用户目标均能对应已验证结果、明确偏差或具体缺口，不能仅凭成功调用数结案。
