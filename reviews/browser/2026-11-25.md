## 证据缺口

- 全部 243 条 unknown 记录均来自 oracle_codex，且均标记为仅有包装器调用点；其中操作类 100 条，另有 41 条条件调用标记。调用点不证明实际执行，也不能按失败计数。“结果缺失为 0”不代表这些内层调用已有独立结果证据。
- 字段更新的 5 条记录均为调用点 unknown（行 776、786、788、792、794）。即使附近存在查询成功记录，摘要也未建立同一目标、预期值与保存后实际值的对应关系，修改结果应列为证据不足。
- 来源根目录缺失、未解析包装器及动态命令标记限制了采集完整性；windows_dsh 回执也不能覆盖 MCP 之外的操作。不能将未采得记录解释为没有操作。
- 未能读取全量包，无法进一步核对用户目标、实际返回内容、跨记录任务关联及后续回读是否支持执行者的完成声明；摘要中的成功声明或观测标识均不能单独补足这些证据。

## 建议

1. **补足包装器的实际执行证据。** 问题是调用点记录大量停留在 unknown。改动：将实际内层调用、返回结果及运行标识关联保存，区分条件未触发与结果不可判定，并列明未覆盖来源。验收：逐条定位包装器记录时，可以找到执行结果，或看到明确的未执行／未知原因；采集缺口仍单独披露。
2. **把业务回读作为完成依据。** 问题是已有执行轨迹和查询调用，却缺少目标与结果对照。改动：对修改任务保存预期结果、保存后重新读取的实际结果及验证引用，并关联到收尾记录。验收：抽查一个已完成修改，可以沿同一任务核对目标、实际结果和引用；未匹配时明确标为未完成或待确认。
3. **修正重复的调用契约与收尾问题。** 问题见多次契约错误及两次无效 memory。改动：依据实际工具契约修正程序、参数和收尾字段；遇到 `OUTCOME_UNKNOWN`，先查最终状态再决定是否重试。验收：后续同类任务不再重复上述已知错误，未知结果均有最终状态或明确的未决说明。
4. **明确运行占用与后续动作的关联。** 问题是两个来源均出现 `RUN_BUSY`。改动：同一运行中的后续操作等待前一操作结束，并引用其状态。验收：后续记录能说明占用操作何时结束、下一操作何时启动，避免相同占用错误反复出现。

## 按评审意见修改

1. 包装器执行证据。采集器按同一会话的 cell ID 关联 exec 与 wait，区分只看到调用点、条件是否触发不明及已有内层结果。用改后的采集器重读同一天的 1,176 条记录，只有调用点的记录由 243 条降至 240 条。原报告五条字段操作中，行 776 返回字段未找到，行 788 返回回读不匹配，行 794 返回更新成功并带观测引用。行 786、792 的循环仍无法逐项归因。以上是对既有记录的复核。
2. 业务回读。字段更新返回预期值和回读值，交接按验收条件带出目标、实际值和观测引用，已回读但不匹配的字段保留失败记录。需在部署后的真实修改中核对同一目标的保存结果。
3. 调用契约与收尾。操作说明加入真实工具接受的程序、内存更新字段和未知结果处理步骤。服务返回需查询的执行标识；下一次同类任务需检查是否仍有相同契约错误或无效收尾。
4. 运行占用。RUN_BUSY 返回占用执行的 ID 和状态；后续执行记录前一执行 ID，采集器保留起止时间。需用部署后的连续操作核对等待顺序。
